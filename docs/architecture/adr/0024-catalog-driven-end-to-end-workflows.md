# ADR 0024: Catalog-driven end-to-end workflows

## Status

Accepted

## Context

Standards Atlas processes single documents and multi-part standards through Docling conversion, AtlasData import, normalization, reference detection, alignment, content enrichment, and export. File paths alone do not describe document identity, family membership, knowledge domains, industry sectors, curated relations, or reusable profiles.

## Decision

Introduce a versioned YAML `StandardCatalog` as a curation and workflow layer outside the canonical `EngineeringDocument`.

The catalog defines:

- controlled `KnowledgeDomain` and `IndustrySector` taxonomies;
- `StandardFamilyDefinition` and `StandardPartDefinition` identities;
- curated typed `StandardRelation` references;
- reusable `StandardProfile` selections;
- source PDF and existing AtlasData locations;
- requested Markdown and Doorstop exports.

An `EndToEndWorkflowService` creates deterministic command plans from a family, profile, or the complete catalog. Multi-part families are converted part by part but imported and exported once at family level. Human alignment review remains an explicit workflow gate. Missing AtlasData is onboarded into a reviewable skeleton and the default run stops there.

The catalog does not become part of `EngineeringDocument`. Detected normative references remain document evidence; curated relations remain catalog metadata.

## Consequences

- Workflows no longer infer identity or part membership from filenames.
- Knowledge domains and vertical industry sectors are independent classification axes.
- One command can select a family or a cross-family profile.
- Human review cannot accidentally be bypassed by the default workflow.
- Future runners can replace subprocess execution without changing catalog or workflow models.

## Regeneration policy

Workflow commands must only use options that are part of the invoked CLI command.
A normal workflow plan does not add replacement flags. Passing `--force` to
`workflow plan` or `workflow run` adds `--overwrite` only to reproducible stages
that explicitly support it: Docling conversion, AtlasData onboarding,
normalization, and alignment. Reference detection, review export, content
enrichment, and document exports retain their own command semantics.

A CLI compatibility regression test renders the real Typer help for every
command generated by representative workflow plans and verifies that all emitted
options are supported by the target command.

### Artifact replacement policy

Workflow steps declare an artifact policy:

- `SOURCE` for expensive upstream artifacts such as persisted Docling JSON,
- `DERIVED` for deterministically reproducible artifacts,
- `REVIEW` for files containing or protecting human review work.

`workflow plan --force` and `workflow run --force` only add a command-specific
replacement option when the step is `DERIVED` and that command supports such an
option. In particular, `--force` never adds `--overwrite` to `docling convert`
and never replaces review exports. Regenerating Docling output remains an
explicit direct CLI operation outside the workflow force policy.
