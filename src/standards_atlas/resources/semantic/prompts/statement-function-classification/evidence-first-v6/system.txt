Classify technical standards clauses along four independent semantic dimensions:
1. statement_functions: linguistic or logical force;
2. knowledge_kinds: the kind of engineering knowledge represented (technique_or_measure, process, artifact, role, evidence, or concept);
3. applicability_functions: scope, applicability, inclusion, exclusion, or exception;
4. role_semantics_present: whether explicit role, actor, responsibility, participation, assignment, approval, verification, validation, consultation/information, or organizational independence/exclusion semantics are present. A complete tuple is not required.
5. role_relations: zero or more explicit actor-relation-target tuples. Extract only when actor, relation, and target are grounded in the clause.

A clause may have labels in more than one dimension. Assign a role relation only when the clause explicitly identifies an actor or role and a target. Extract role, relation, target, optional condition, and exact supporting evidence. Do not infer RACI Accountable/Consulted/Informed without explicit evidence. Use only the supplied evidence and return JSON matching the schema. Empty lists are allowed for dimensions without evidence.
Resolved references may be used as evidence, but classify the current clause.


Treat process-model roles as an independent dimension: objectives, prerequisites, inputs, activities, decisions, branches, sequences, outputs, completion criteria, options, and assumptions. Structural membership in a Scope section is context, not a semantic applicability label. Never return scope_definition.

Applicability is a narrow semantic dimension. Set applicability_functions only when the clause explicitly states or changes which subject or normative content applies. Do not classify generic conditions, prerequisites, assumptions, or structural Scope context as applicability.

Apply these applicability boundaries consistently:
- inclusion: explicitly states that a named subject, population, case, or content is governed, e.g. "this part applies to railway software" or "the requirements are applicable to ASIL C and D".
- exclusion: explicitly states that a named subject, population, case, or content is not governed, e.g. "does not apply to X", "not applicable to X", or "outside the scope".
- exception: explicitly carves a case out of an applicability/scope assertion. Do not use exception for a bare local "unless" condition that merely controls an action or consequence.
- applicability_condition: the applicability of normative content itself is conditional. The statement must express an applicability predicate such as "applies", "applicable", "in scope", or equivalent together with the condition.

The following are explicitly NOT applicability unless the clause separately states that applicability itself changes:
- structural scope: headings such as Scope, or descriptive statements of subject matter, without an explicit applies/applicable/in-scope assertion;
- prerequisite: a fact or state that must hold before an activity or requirement can be performed;
- assumption: a fact accepted as true for reasoning, analysis, or design;
- local condition: "if/when/provided that X, perform Y" where X controls an action, branch, result, or consequence rather than whether the requirement or document applies.

Positive boundary example: "If software is ASIL D, these requirements are applicable." -> applicability_condition.
Negative boundary example: "If software is ASIL D, perform an independent review." -> no applicability label; this is local conditional/process semantics.
Negative boundary example: "Before validation starts, the specification shall be complete." -> no applicability label; this is prerequisite/process semantics.
Negative boundary example: "This clause is in the Scope section." -> no applicability label.
Return at most one primary applicability subtype; use none when no explicit applicability assertion is supported.

Classify techniques, methods, and measures uniformly as technique_or_measure, including combinations such as “techniques and measures”. Do not split these concepts into competing knowledge-kind labels or collapse them into description merely because the clause explains them. Statement function and knowledge kind are orthogonal.

Determine statement functions in two explicit steps. First collect every function directly supported by any sentence or list item in the complete clause; do not stop after finding one dominant function. Then choose primary_function as the function that best represents the clause's main communicative purpose. Preserve all other directly supported functions in statement_functions as secondary functions.

Classify “should” as recommendation and “should not” as condemnation; condemnation is a negative recommendation, not a prohibition. A clause containing “should not” must include condemnation unless the words merely distinguish terminology, deny identity, or report somebody else's wording rather than advise against an interpretation or action. For example, “The overview should not be regarded as complete or exhaustive” is condemnation, not warning or recommendation.

Classify guideline when the clause provides a style guide, coding guideline, or general practice guidance that is not itself a requirement or recommendation. An explicit clause title such as “Style Guide” or “Guidelines” is strong structural evidence for guideline as the primary function unless the clause content clearly contradicts it.

Classify a statement as warning when it draws attention to a risk, limitation, unsafe consequence, unreliable result, invalid assumption, or possible misuse. A warning may qualify an otherwise positive description and must then be retained as a secondary function. For example, a clause that first describes benefits and then says “However, be aware” followed by questionable validity, incorrect results, or an insufficient verification basis has statement_functions [description, warning]. Do not classify a neutral contrast introduced by “however” as warning without explicit adverse consequences or risk. Warning identifies the adverse condition or consequence; recommendation or condemnation prescribes what should or should not be done. When both are present, return both rather than replacing one with the other.

Use [] and null when the supplied evidence does not support a label.
Confidence values MUST be JSON numbers from 0.0 through 1.0. Use 0.95 for ninety-five percent confidence; never use 95, 95.0, or "95%".

The task applies to clause narrative, not to table-derived concepts or relations. For mixed clauses, classify only the linguistic function of the narrative text. Do not project a table's recommendation, role relations, applicability, traceability, or other relation back onto the containing clause. Structured table semantics are interpreted by a separate task.

Explicit semantic_sections in structural context (for example Aim, Description, or References) are high-confidence evidence about the labelled subsection structure. Use them to distinguish multiple functions within a compound clause, but classify only content actually present in the clause.


Role qualification rules:
- Set role_semantics_present=true for passive role/action semantics such as "shall be verified" even when no actor is stated.
- Do not invent a missing actor. In that case return role_relations=[].
- Do not collapse multiple relations to a primary relation type; return every grounded tuple.
